## Summary

データ管理に「このバックアップを復元テスト」を追加 — 選択したバックアップをユーザー指定の隔離ディレクトリへ**本物の復元機構** (`restore_backup`) で復元し、独立に再検証する。本番データ・プロセス・キャッシュ・資格情報ボールトには一切触れない。

Refs #992

新規 `htdt/restore_drill.py`: `run_restore_drill` は archive（`inspect_backup` で検証 — 第2の検証器は作らない）→ restore（空の隔離 dir へ実復元）→ verify（SQLite integrity、着地ファイル全件 manifest 再ハッシュ、`_assert_staged_database_openable`、`audit_native_authority_graph` を clone に再生、read-only シーン件数）→ migrate（移行必要な旧形式のみ sandbox 内で `execute_native_upgrade`）の4フェーズ。`managed_data_fingerprint` 前後一致で本番不変を実証。評決語彙 `restorable/restorable_with_conditions/failed/not_verifiable` は issue の要求区分に対応し、署名欄の非存在は `skipped` として正直に報告する。`claims`（証明済み）と `non_claims`（別PC移行/物理復旧/運用者受入 — 本演習では証明不可）を常に分離。

配線: `DataOperationKind.RESTORE_DRILL`（CANCELLABLE、`lifecycle_mode='none'` — live ツリーは指紋採取のみで quiesce 不要）+ `restore_drill_completed` シグナル + データ管理画面の世代行ボタン・隔離フォルダ選択・結果カード・「前回の復元テスト」行。演習ジャーナル `restore-drill-results.jsonl` を persisted-data registry 登録（backup 対象外）。

`test_issue_992_restore_drill.py` 8件 — 正常系全脚 pass+本番 SHA 不変、改竄/不在→failed、sandbox 包含拒否、キャンセル伝播、既存バックアップ非削除、旧形式アーカイブの conditional+移行脚。33件緑。
