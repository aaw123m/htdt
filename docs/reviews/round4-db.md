## Fixed in this branch

| # | Severity | Location | Finding | Fix |
|---|----------|----------|---------|-----|
| 1 | high | `capture_ingestion_transaction.py` `_externalize_inline_source_payloads` | **Unverified digest-keyed copy + blanket inline wipe.** The v4-era externalization ran `INSERT OR IGNORE INTO htdt_content_blobs SELECT payload_sha256, byte_count, payload_blob … WHERE length(payload_blob) > 0` — keying blobs by the *recorded* digest without ever hashing the bytes — then `UPDATE … SET payload_blob = X''` on every row. If any row's bytes didn't hash to its recorded digest, the blob store got a mis-keyed row (any reader then fails closed on the shared digest, including for healthy rows that legitimately own it under `INSERT OR IGNORE` first-writer-wins) and the corrupt row's inline bytes — its only copy — were erased anyway. Contrast with the adjacent `_compact_legacy_mesh_bindings`, which does verify `sha256(embedded) == geometry_sha256` before rewriting. | Rewritten as a Python loop: each row's inline bytes are externalized through `store_content_blob(..., expected_sha256=...)` (post-write rehash + collision fails closed) only after `sha256(payload) == payload_sha256` verifies — the same check readers apply — and only then is the row's inline blob cleared. Unverified rows keep their inline bytes untouched. Digest-only verification is deliberate: a sha-valid row with a stale `byte_count` is *repaired* by externalization (readers ignore `byte_count` on the blob path), whereas keeping it inline would leave it permanently unreadable. Regression test: `test_v3_externalization_never_stores_unverified_inline_bytes` (mutation-verified against the old SQL). |
| 2 | medium | `cad_repository.py` `save_authoring_constraints` | **Head-resolution TOCTOU — lineage fork possible.** The previous head was resolved via `authoring_constraint_head` on *separate* connections before `BEGIN IMMEDIATE`; the insert + `ON CONFLICT` head-pointer upsert then committed unconditionally. A concurrent save landing in the gap would be silently superseded out of the lineage: its revision row stays in `authoring_constraint_revisions` but the pointer is overwritten and nothing ever `supersedes_id`s it again — a dropped head invisible to `list_authoring_constraint_revisions` ancestry. Every sibling single-head store (scene revisions `save`, assumption/decision repo, design-checkpoint restore) does its compare-and-swap *inside* the write lock. | Added `_authoring_head_pointer_id()` which re-reads the `authoring_constraint_sets` pointer row on the write connection under `BEGIN IMMEDIATE`; a pointer that moved since pre-lock resolution raises the new `AuthoringConstraintConflictError` (ValueError, mirroring `SceneRevisionConflictError`) instead of writing. The pre-lock `authoring_constraint_head` call is unchanged, so corrupt authorities still fail closed before the lock. Regression test: `test_constraint_save_rejects_a_head_that_moved`. |

## Findings — flagged, not implemented

| # | Severity | Location | Finding | Remediation sketch |
|---|----------|----------|---------|--------------------|
| A | medium | `cad_schema_ddl.py` `authoring_constraint_revisions` | **No `UNIQUE` on `supersedes_id`, no `REFERENCES`.** The lineage fork fix #2 prevents at write time is not schema-enforced: two revisions naming the same parent are structurally legal, and `scene_revision_id`/`supersedes_id` carry no foreign keys, so a repair/restore bug could still mint dangling lineage. | v11 migration rebuilding the table with `UNIQUE(document_id, supersedes_id)` (SQLite treats NULLs as distinct, so multiple root revisions stay legal) and `REFERENCES scene_revisions(revision_id)`. Deferred: a rebuild must first tolerate forks already present in field databases — needs a quarantine rule, not a small diff. |
| B | low | `cad_schema_ddl.py` — ~291 column-level `TEXT PRIMARY KEY` declarations | **No `NOT NULL` on non-integer primary keys.** SQLite allows NULL (and multiple NULLs) in a `TEXT PRIMARY KEY` column — e.g. `htdt_content_blobs.payload_sha256`, `capture_source_evidence.source_evidence_id` would accept NULL-keyed shadow rows that reads can never address. Every writer today supplies validated non-None ids via pydantic models, so this is a schema-level hardening gap, not an active bug. | Cheapest: a `test_cad_schema_ddl_contract` addition asserting every column-level `TEXT PRIMARY KEY` is rendered `NOT NULL` for *new* tables going forward; a mass rebuild for existing tables is churn — alternatively accept and document the convention. |
| C | low | ~20 modules with raw `sqlite3.connect` and no `PRAGMA foreign_keys=ON` (`project_lifecycle`, `system_expansion_workflow`, `native_row_integrity`, `migration_guard`, `native_backup`, `application_pages`, `default_document`, `data_relocation`, `database.integrity_problems`, `native_authority_audit`, …) | **Inconsistent FK enforcement on secondary connections.** Verified none of these connections currently write to any of the 93 FK-bearing tables (they are read-only paths, backup/restore `sqlite3.Connection.backup` targets, or write to FK-free `htdt_*`/journal tables). Benign today, but a future edit that adds a write to a REFERENCES table on one of these connections silently skips FK checks. | Contract test: statically assert any module issuing `INSERT/UPDATE/DELETE` against an FK-bearing table opens via `connect_sqlite`; or migrate these to `connect_sqlite` wholesale (harmless for readers). Deferred — mechanical but touches many files. |
| D | info | `cad_project_template.py` `_rollback_template_creation` | **Rollback delete list is table-explicit and doesn't cover `scene_revision_labels`/`editor_view_states`.** Unreachable today — the template flow never writes labels or view state for the fresh revision — but a future label write inside the flow would silently leak a child row past the FK-check-free path. | Note the invariant in `_rollback_template_creation`'s docstring, or add the child-table deletes for defense-in-depth. |

## Verified clean (no action)

- **Transaction scope**: every mutating repository path uses `with closing(conn) as conn, conn:` + `BEGIN IMMEDIATE` (scene revisions, recovery snapshots, named views, payload stores, measurements/datasets/comparisons, checkpoints, inbox, connected space, semantic promotion, template creation, deletion). No nested or interleaved `BEGIN`s; a script sweep found zero `commit()` calls inside loop bodies. The codebase's own "don't open a sibling connection while the write lock is held" rule (documented in the prediction/adaptive/standards repositories) is consistently honored — fix #2 keeps that contract by re-reading the pointer on the lock-holding connection.
- **Compare-and-swap inside the lock**: `SceneRepository.save` (duplicate-root + stale-parent rejection), `save_recovery`, assumption/decision repo, `cad_project_template` shared-store creation, `cad_design_checkpoint` restore (scene head + workspace + record in one commit), `capture_inbox`, `purge_capture_revision` (plan recomputed under lock), `delete_project` (blockers re-evaluated under lock, `expected_plan` fingerprint), and `run_storage_gc` (reachability recomputed per-candidate under lock) all re-validate under `BEGIN IMMEDIATE`.
- **FK-check-before-commit**: both bulk-delete authorities that relax ordering (`delete_project` with `PRAGMA foreign_keys=OFF` outside the txn, `purge_capture_revision`) run `PRAGMA foreign_key_check` inside the transaction and roll back on violations.
- **DDL drift / registry**: `NATIVE_SCHEMA_TABLES` (345 names) covers all 318 baseline `CREATE TABLE`s plus the migration/convergence-created tables (`native_schema_metadata`, `native_schema_migrations`, `htdt_content_blobs`, `physical_space_models`, capture convergence shapes); `test_cad_schema_ddl_contract` enforces it. No ad-hoc `CREATE TABLE` outside the baseline + registered convergence functions (`native_row_integrity`'s match is a regex literal).
- **Migration chain**: `_MIGRATIONS` applies v1..v10 strictly in order from the persisted `native_schema_metadata` version — no skipping path exists; interrupted-restore recovery runs unconditionally before the signature memo short-circuit. `migration_guard` wraps the legacy store: pre-migration integrity + `foreign_key_check`, versioned pre-migration zip, bounded member extraction (path/size/count caps, symlink/special rejection), post-restore version re-validation.
- **Blob/content integrity**: `store_content_blob` re-hashes the stored row post-write and fails closed on a digest collision; `read_content_blob` verifies `byte_count` + sha256 on every read; `run_storage_gc` content-verifies each orphan candidate (file bytes must hash to the digest name) before deleting; scene revisions re-verify `content_hash` from `payload_json` on read; recovery snapshots likewise; measurement comparisons replay the pinned algorithm against bound datasets at save *and* on authoritative reads.
- **Backup/save round-trips**: `native_backup` uses the SQLite backup API (consistent snapshot under writers), sha256 manifests, entry-vs-digest verification, and a post-restore health check; `data_relocation` snapshots via the backup API and journals the move for crash recovery.
- **Orphaned rows**: `delete_project` deletes via owned predicates with semantic-ownership assertion; `purge_capture_revision` refuses while dependents exist; `htdt_content_blobs` GC deletes only digests nothing references; `repair_authoring_constraints` intentionally clears only the head pointer, retaining immutable history (correct per #843). `_payloads` corrupt-row cleanup targets exact `(document_id, key)` identity; the `record_id or document_id` fallback for a falsy key is a benign no-op (deletes nothing).
- **Upsert/UNIQUE usage**: every `INSERT OR REPLACE`/`ON CONFLICT` site (`scene_document_heads`, `scene_recovery_snapshots`, `authoring_constraint_sets`, payload stores, camera/view state, site/session authorities) is keyed by a declared PK/UNIQUE column — `ON CONFLICT` targets match real unique constraints; `INSERT OR IGNORE` on content/lineage/asset tables is digest-or-PK-keyed idempotent dedup, not data-swallowing (except finding 1, fixed).
- **Empty `IN ()` placeholder**: `capture_retention._execute_plan`'s `IN ({placeholders})` can't see an empty `run_ids` on a non-absent plan, and `expr IN ()` is valid SQLite anyway.
- **No WAL**: the store is rollback-journal only by invariant (verified in round 2) — readers never block on the write lock, which is exactly why the pre-lock head read in finding 2 could go stale.
