## Summary

`WasapiAudioBackend` was a fail-closed stub (`available()=False`, empty enumeration, `open_stream` raising `BackendUnavailableError`) — the shared structural blocker for #869/#875/#876/#877/#886. This implements it for real over raw COM/ctypes — `IMMDeviceEnumerator` → shared-mode `IAudioClient` render+capture — with **no new dependency** (stdlib `ctypes` only, per repo venv conventions).

Architecture (`backend/src/htdt/cad_wasapi_io.py`, new):
- `WasapiDriverBase` / `WasapiRenderClientBase` / `WasapiCaptureClientBase` — a narrow injected seam (enumerate, default-endpoint, open clients). `CtypesWasapiDriver` implements it over real COM; tests inject a scripted fake on the same seam so every non-hardware path is verifiable without audio hardware.
- `_WasapiStream` — the pump loop behind `open_stream`: capture starts first (recording honestly contains pre-onset room noise), render buffer pre-fills, render writes go only to the bound channel, `AUDCLNT_BUFFERFLAGS_*` map to honest `CaptureEvent`s (`DATA_DISCONTINUITY`→xrun, `TIMESTAMP_ERROR`→drift, `SILENT`→zeros substituted), `|sample|≥0.9999999` counts clipped, default-endpoint change / endpoint invalidation / capture deadline → `device_lost`/`truncated` — never papers over a failure.

`WasapiAudioBackend` (`cad_sweep_acquisition.py`):
- `WasapiAudioBackend(driver=...)` — default lazy `CtypesWasapiDriver` (Windows only); injected driver for tests.
- `available()` stages precise reasons: non-Windows host, driver init failure (e.g. Windows Audio stopped), enumeration failure, missing render/capture endpoint — `unavailable_reason()` is never a bare 'unavailable'.
- `enumerate_devices()` maps `WasapiEndpointInfo` → honest `AudioDeviceInfo`: shared mode binds only the endpoint mix rate, `supports_float32` is probed via `IsFormatSupported`, and the real `channel_mask` + per-channel labels (new optional `AudioDeviceInfo` fields) use the #621/#876 vocabulary (`FL/FR/C/LFE/SL/SR/SBL/SBR/TFL/…`); mask-less channels are labelled `ch<N>`, never guessed. `stereo_pair_channels` uses `CANONICAL_SPEAKER_PAIRS`.
- `open_stream` gates on `available()` (`BackendUnavailableError`) then mirrors `FakeAudioBackend`'s validation order: unknown device → `DeviceNotFoundError`; direction/channel/rate/format → `UnsupportedConfigurationError`; exclusive-mode contention → `BackendUnavailableError` with actionable text; unsupported bind → `UnsupportedConfigurationError`. A failed second bind closes the first client.

Honesty: `backend_version` bumped to `'wasapi-audio-io-1'`; `backend_is_simulated` stays `False` for this backend (it is the real path — runs through it may claim real evidence per existing verdict rules); no fail-closed check anywhere was weakened (pre-roll, SNR window, xrun/truncation/device-loss semantics identical to the fake). Two JA UI labels claiming "このビルドでは未実装" now report live availability (`measurement_page_workspace.py`); stale "stub" wording in `headless_cli` docs + `issue-869-native-sweep.md` updated. No new sealed tables → schema stays v112.

Tests (`test_issue_869_wasapi_backend.py`, 41 tests + guarded smoke): mask labels + vocabulary parity, all availability branches, enumeration mapping, `open_stream` validation order, pump-loop outcomes, and an injected-driver engine run to `completed`. Stub-assuming tests in `test_issue_869_native_sweep.py` now inject a deterministic empty driver (they were constructing the real backend and assuming it stays unavailable — true on this box only because Windows Audio is stopped). Result: **121 passed, 1 skipped** (real-hardware smoke — this box exposes no endpoints).

Notes for review:
- `tests/test_issue_884_support_bundle.py::test_audio_context_collector_lists_stub_honestly` still asserts wasapi `available() is False` — passes here (no endpoints) but is now host-dependent; left untouched as a sibling slice's file.
- Test env deviation: this box only has Python 3.13 (`backend/.venv`); the blueprint's 3.12.10 install path is unchanged but failed in the snapshot build — tests ran on 3.13.
- Device-only remainder (in the new doc): real-endpoint capture validation, `IMMNotificationClient`-driven default-change detection (current polling adds ≤ ~0.25 s detection latency — documented honestly), exclusive mode, event-callback pumping.
