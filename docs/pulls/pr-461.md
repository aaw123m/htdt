## Summary

`_recover_journal_locked` promoted any staged root that happened to contain `htdt.sqlite3`, regardless of the journal phase. But `PREPARED` is written *before* the copy phase — a `kill -9` between the `sqlite3.backup()` and the carried-component copy leaves a staged root whose database was never verified (`STAGED_VERIFIED` is only journaled after `_verify_staged_root` + `assert_native_authority_graph`).

Two confirmed failure modes (probed dynamically):

- **Launch brick**: torn staged db → `_verify_staged_root` throws `sqlite3.DatabaseError` inside recovery → every subsequent startup hits the same journal and re-throws; the intact source sits behind an unrecoverable journal forever.
- **Silent data loss**: complete-looking staged db but mid-carried-component copy → verification passes → the incomplete root is promoted and reported as `destination_promoted`/`completed`, silently dropping commissioning plans, `automatic-backup-policy.json`/`automatic-backup-state.json`, upgrade recovery generations and diagnostics.

```python
if (
    not destination_database.is_file()
+   and journal.phase != 'PREPARED'
    and _staged_database(journal).is_file()
):
    _verify_staged_root(staged); os.replace(staged, destination)
```

`PREPARED` residue now always falls to the pre-existing abort path (`aborted_before_promotion`: rmtree staged + clear journal), which is the complete-or-nothing contract the phase already implies. Later phases (`STAGED_VERIFIED`, `DESTINATION_PROMOTED`, `SOURCE_PARKED`, `BOOTSTRAP_SWITCHED`) are unaffected — a verified staged copy can still be promoted to complete the cutover.

Two regression tests in `test_data_relocation_cutover.py` cover both crash windows (complete-looking db + torn db); both fail on the pre-fix code with the real error modes.
