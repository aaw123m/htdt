## Summary

Fixes a crash surfaced during REV73: a `NativeWorkerPool` task record could outlive its QThread's C++ object, after which `_detach` (and every other path touching the record) raised `RuntimeError: Internal C++ object (QThread) already deleted`. Worse, one stale record mid-`_detach_all` aborted the whole loop, leaving a live sibling thread parented to a pool that was then destroyed — `~QThread` on a running native thread terminates the process. `DataManagementController._detach_active_thread` had the same exposure and additionally leaked its `_LINGERING_OP_THREADS` pin when `setParent` raised inside the `destroyed` handler.

Root cause: `start()` connected `finished -> thread.deleteLater` *before* `finished -> _thread_finished`. A typed `sendPostedEvents(DeferredDelete)` flush between the two queued metacalls killed the C++ object while `_tasks[key]` still pointed at it. `data_management._start` already had the right order; the pool now matches it.

Fix shape (both files follow it):

- `isValid(thread)` early-out releases stale records; pin + `setParent`/`connect`/`isFinished` wrapped in `try/RuntimeError` — a mid-detach death pops the pin instead of leaking it.
- `_detach_all`, `_stop_tracked`, `drain_*`, `cancel_*`: per-record guards so one stale record can't abort the loop; dead records release honestly as *stopped* and are never re-reported as running (`active_count` skips dead wrappers).
- `_thread_finished` sweeps dead records when a late `finished` metacall arrives with `sender() is None` or `property()` raises.
- `_LINGERING_*_THREADS` drains pop dead keys on `RuntimeError` (no signal will ever fire to release them).

## Evidence

Regression tests in `test_worker_teardown.py` reproduce the reported traceback verbatim on old code (`thread.setParent(None)` → `RuntimeError` inside the `destroyed` lambda, plus a leaked pin `lingering 2 != baseline 1`), and the pool-destroy test aborts the whole test process (exit 127 — `~QThread` while running). With the fix:

- `test_worker_teardown.py` + `test_native_worker.py`: **32 passed**
- `test_round19_worker_contracts.py` + `test_round17_concurrency.py` + `test_issue_1014_capture_watch_isolation.py`: **22 passed**

Coverage: detach after natural finish, detach after C++ deletion, `shutdown()`/`start()` over a dead record, pool destroy with dead+live records, late `finished` metacall for a dead sender, and the `_LINGERING_OP_THREADS` equivalents for the controller including destroyed-mid-operation.

Root cause + fix shape documented in `docs/issues/issue-worker-detach-runtimeerror.md`.
