## Summary

最適化ワークスペースの6ページ（探索設定／候補／比較／介入計画／ばらつき耐性／測定・検証）はフラットな兄弟タブで、初回利用時の正規順序——部屋を保存 → 探索設定を保存 → 候補を生成して適用 → 実測候補を記録・計測 → 検証条件を事前登録 → 比較と検証を確認——をタブ列は一切表現していなかった。REV32-GUIDE が測定ページに入れた番号付きジャーニー（PR #478）と同型のガイドを最適化ワークスペースにも追加し、「今どの段階か・次は何か」を永続状態から即座に読み取れるようにする。

- 新規 `optimization_journey.py`: `evaluate_optimization_journey(**signals)` が永続シグナルを6ステップ（done / current / pending / blocked + detail + 遷移先）に評価する純粋関数。唯一のハードゲートは部屋の保存（全 spec が正確な revision + content hash に束縛されるため、保存前は下流すべて blocked）。介入プランナー・ばらつき耐性は任意の寄り道として主筋から除外し、完了時ヒントにのみ言及。
- `OptimizationWorkflowWorkspace`: ページスタック直上に「最適化の手順」カード（番号ボタン列 + `n/6` 進捗 + 「次にやること」ヒント + 「現在の手順を開く」ボタン）を常駐化。各ステップは `WorkspaceDeepLink(WorkspaceId.OPTIMIZATION, page)` 経由で所有ページへ遷移（`on_navigate` 未接続のスタンドアロンでは `select_section` にフォールバック）。scene ステップのみ `WorkspaceId.ROOM/geometry` へ遷移。
- ライブ追従: `activate()` / `select_section()` / `refresh_from_authorities()` に加え、`statusChanged`（全永続化経路が最後に発行するコントローラの statusBar メッセージ＝汎用ミューテーションパルス）にも接続し、spec 保存・候補適用などの場内変更でもストリップが即時再評価される。
- apply ステップの判定は正直な永続証跡のみ: 測定プランの存在（適用済み revision の上にしか作れない）またはヘッド revision が spec のソース revision の子孫であること（32 ホップの `parent_revision_id` 遡行）で検出。候補生成自体はセッション内のみの非永続操作（`candidate_set_sha256` で決定論的に再生成可能）なので apply ステップに折り込み、虚偽の進捗を表示しない。
- 全リポジトリ呼び出しは try/except で空シグナルに退化（fail-closed な `inspect_for_search_spec` 含む）し、評価クエリは spec あたり ≤7 件・最大16 spec に制限。
