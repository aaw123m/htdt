## Summary

REV28 concurrency audit fixes: two proven cross-thread defects.

**1. `SceneRepository`/`CadSystemVariantRepository` pooled read connections — use-after-free on cross-thread `close()`.** `close()` released each pooled `_SharedReadConnection._inner` unconditionally while other threads could be inside `execute`/`fetch` on the same handle; a stress probe (4 readers × `close()` × 400) produced an interpreter access violation (segfault). `_SharedReadConnection` now borrows under a per-proxy `RLock`: `__enter__`/`__exit__` acquire/release it, `close()` calls `_close_for_release()` which takes the same lock — a release waits for the in-flight borrow to unwind instead of freeing mid-read. A released slot lazily re-opens via a `_connect_factory` lambda so reads keep working after `close()` (the pool slot was already cleared, so the reopen is one-off). The four bare `closing(self._read()) as connection:` sites gained `, connection:` so the `with` borrow (and its lock) actually engages — bare `closing()` never called `__enter__`.

**2. `CaptureReceiverService.handle_delivery` — concurrent duplicate delivery corrupted the ledger and suppressed the listener.** Two simultaneous deliveries of one `delivery_key` both pass the `_get_delivery` dedup read, both reach `stage()` (serialized; loser gets `created=False`), then race `_record_delivery`. Before this fix, if the loser recorded first the row stayed `already_staged` forever and `_delivery_listener` fired zero times; if the winner recorded first the loser also saw `accepted` and the listener fired twice. Now `_record_delivery` upgrades a stored `already_staged` → `accepted` when the stager's verdict lands, `handle_delivery` remaps a non-creator's `accepted` receipt to `already_staged` (same replay semantics as the sequential `prior` path), and the listener fires only for `staged.created` — exactly-once acceptance announcement, verified across both record orders.

## Tests

- `test_close_while_other_threads_read_is_safe`: 4 reader threads hammer `get()` while `close()` runs 50×; asserts zero exceptions and that reads still succeed after close (lazy reopen).
