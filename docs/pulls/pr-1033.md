## Summary

Every `physical`/`manual` gate in `scripts/issue_lifecycle_manifest.yaml` now compiles to a sealed **minimal-step operator plan** (3 auto checks + exactly 1 human attestation step) plus a sealed **acceptance-run record**, wired into the `htdt` CLI as a new `gates` family:

- `htdt gates plan` — derive `GateOperatorPlan` (`gplan-…`) per selected gate; deterministic seal (pure function of manifest bytes → re-planning is idempotent); `--spec` filters `issues`/`kinds`, `--out` writes a plan bundle.
- `htdt gates run --plan-id|--plan` — executes the plan: environment snapshot, `evidence_refs` repo-local resolution (same rules as `issue_lifecycle.py`), prior-run listing, then the single operator step which resolves **only** from `--attest` (`--evidence FILE` sha-pins artifacts). Verdict derives fail-closed: `gate_satisfied`→exit 0, `awaiting_attestation`→`blocked` (3), `steps_failed`→`failed` (2). `--out` writes a `htdt-gate-run-export-1` envelope.
- `htdt gates import --run-file` — re-validates the envelope and re-derives `run_sha256`/`run_id` inside the model validator, so a tampered export can never enter the store; re-import reports `already_imported`.
- `htdt gates list`, `records list/export --kind gate_plan|gate_acceptance_run`.

Honesty: `gate_satisfied` means auto checks passed **and** an operator attested — `non_claims` states the attestation is human, not machine proof, and the record is execution evidence, not domain acceptance of the issue.

New sealed tables `cad_gate_operator_plans` / `cad_gate_acceptance_runs` behind `_SealedStore`, schema v114 (`_migrate_113_to_114`), with full authority wiring: `NATIVE_SCHEMA_TABLES`, `_ROW_BINDINGS`, audit replay probes + repo factory, lifecycle table JA labels.

Tests: `backend/tests/test_rev72_gate_plans.py` — 13 tests covering manifest→plan derivation over the real manifest, honest verdicts, seal tamper rejection, repository round-trip, and CLI exit lattice incl. dry-run non-mutation. Full schema/integrity/audit/headless sibling suites still pass.
