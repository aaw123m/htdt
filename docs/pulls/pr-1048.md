## Summary

Refs #1023

The アクティビティ page listed every project's revisions under the current project — `list_recent_revisions` ran `WHERE detached = 0 ORDER BY seq DESC LIMIT ?` with **no `document_id` filter**, so with several projects in one app DB, foreign revisions appeared on the page and could crowd out all 50 rows of the current project's own history.

**SQL scoping (filter at the query, never hide rows in the UI):**
- `list_recent_revisions(repository, limit, *, scope, document_id, offset)` gains a typed `RevisionListScope`: `'project'` adds `AND document_id = ?`; `'global'` is the only explicit all-projects opt-in; `'project'` without a document id (or an unknown scope) raises `ValueError` — fail closed.
- New `count_recent_revisions` (same scope, `COUNT(*)`) backs the pager totals; `list_known_document_ids` (`SELECT DISTINCT document_id WHERE detached = 0`) enumerates projects for the global merge.

**Honest scope UI (`ActivityPage`):**
- Page-level 表示範囲 combo: 「このプロジェクト / 全プロジェクト」; forced to global + disabled when no project is bound. All three section headings state the scope (操作（このプロジェクト（<名前>）), プロジェクトタイムライン（…), リビジョン履歴（…)).
- Operations split: rows whose `project_ref` matches any ref the project answers to (document_id, project_id, display name) stay under このプロジェクト; app-global/unscoped and foreign rows move to a separate その他の操作（アプリ全体・他のプロジェクト）section.
- The per-event プロジェクト column is shown only in the global view.

**Timeline filters + paging:**
- 種類 combo (JA groups over the closed `ActivityEventKind` set: 保存, 計測, キャプチャ, 校正, 健康点検, etc.), 期間 combo (今日/過去7日間/過去30日間), free-text search, `全N件 · X–Y件を表示` counts, and 前へ/次へ paging — the 50-row cap can no longer hide the past.
- The timeline remains the canonical `CadProjectActivityService.events` projection; the global view merges each document's own projection — no parallel audit log.

**Deep links + stable selection:**
- Revision rows link to `SCENE_REVISION` `NavigationTarget`s (部屋 → history) carrying the row's own `project_id`; foreign timeline rows get `project_id` stamped at activation — both route through the guarded `_switch_project`, so another project's revision can never activate silently in the current one.
- All re-renders (`refresh()`, filter, paging, scope change) go through `_preserve_selection`, rebinding by `(event_id | revision_id, document_id)` / `operation_id` — never by row index.
