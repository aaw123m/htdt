## Summary

REV65-CORE review of the post-REV61 mission/field-return pipeline (`capture_receiver`, `field_return_ingestion`, `mission_reconciliation`, journey/envelope wiring).

Defect fixed: `apply_returned_tasks` deduplicated only on `UNIQUE(contribution_id, task_id)`, so a second field-return contribution carrying the same mission task minted a second `field_return_applications` row — potentially with a conflicting `applied_target_id`/`decision_id`. A mission task now binds once across all contributions: bulk apply silently skips the already-bound task (idempotent, same-contribution replay unchanged), and an explicit `task_ids` request for a cross-bound task raises `MissionReconciliationError`.

Tests: `test_rev65_core.py` (2 regression tests); `test_apply_flags_refs_the_container_cannot_resolve` updated — its second contribution now carries a different mission task per the new rule.

## Findings (report only)

- `capture_receiver.py` broad `except Exception` at wire boundaries is semantically right (structured reject / logged) but lacks `# error-boundary:` markers — the marker AST-guard only covers the #815 scope modules.
- Field-return staging commits the artifact before the header-vs-artifact `artifact_id` agreement check — a reject still leaves the staged row (content-addressed, survivable; domain judgment).
- `stage_rejected` binds the declared (unverified) sha to the rejection record; recording the computed sha beside it would be more honest.
- Verdict mapping unknown-string → 'failed' is intentional fail-closed; 'superseded' self-report is unreachable in the current wire vocabulary.
