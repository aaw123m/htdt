## Summary

Implements #833 — a reproducible local/release-candidate software verification gate that answers "was this exact source revision software-verified?" and binds the answer into release artifact provenance.

**Core pieces:**

- `scripts/release_verification_manifest.yaml` (`version: 1`) — the single versioned manifest. 13 check classes in deterministic order (dependency-lock, canonical-references, package-boundary, schema-migration, authority-invariants, persistence, backup-restore, measurement-evidence, recommendation-gating, solver-provenance, golden-path-preflight, native-startup-smoke, package-smoke), each with `required` / `include_in_dev` / `requires_capability`, plus `external_gates` declaring owned-room, GPU, and UX160 acceptance as separately typed gates the software verdict never covers.
- `scripts/run_release_verification.py` — the single documented entry point: `python scripts/run_release_verification.py --profile release`. Reuses `verify_open_issues.py`'s bounded-subprocess machinery (Job-Object kill-on-close, attempt retries, `_check_env`, `_env_fingerprint`). Emits `release_verification_evidence.json` (schema `htdt-release-verification/1`: commit sha + dirty + branch, manifest sha256, runner self-sha256, toolchain + lock-file sha256, per-check status/log/skip_reason/attempts) plus `release-verification-<date>.md`. Verdict `passed` / `failed` / `incomplete` — interruption, partial runs, and required-check absence can never become PASS. Optional classes skip only with an explicit probe reason; required classes are schema-forbidden from needing a capability.
- `scripts/package_smoke.py` — optional class: verifies a built `dist-native/HTDT` package's `build_info.json` matches the checked-out commit and lock hash, and `HTDT.exe --version` reports the same revision.
- `scripts/verification_evidence.ps1` — `Get-VerificationBlock` fail-closed validator: only `passed` + `run_completed` + `profile: release` + `coverage: full` + same-commit evidence yields `verified`; anything else records `unverified`/`rejected` in the release manifest, so an artifact from an unverified revision can never look verified.
- `scripts/build-installer.ps1` — `-VerificationEvidence` embeds the validated block (incl. `evidence_sha256`) into `htdt-release-manifest/1`; `-RequireVerification` makes anything non-verified fatal.
- `.github/workflows/build-windows-artifacts.yml` — `run_software_verification` input (default on) runs the release profile before packaging, uploads evidence as an artifact, and wires the binding into installer + portable manifests. No PR CI is added — repo policy unchanged.

**Distinct profiles:** `--profile release` (full coverage → `coverage: full`) vs `--profile dev` (manifest-declared subset) vs `--classes` (scoped). `coverage` is recorded honestly, and only `full` release evidence binds as `verified`.

**Verified locally:** dev profile run green end-to-end (6 checks), `--dry-run` resolves the full plan incl. capability probing; 29 new tests in `backend/tests/test_release_verification.py` cover manifest schema, fail-closed verdict semantics, end-to-end runner behavior (incl. interrupt→incomplete), and the binding pins.
