# GUI visual design execution plan: desktop shell, Room CAD surface, data workspaces and acceptance specification


## Purpose

This issue is the **visual/UI execution plan** for the native HTDT desktop application.

It does not replace #118. #118 owns the workflow-first product/IA direction.

This issue freezes the next design layer in enough detail that implementation can proceed without repeatedly making local visual decisions inside individual widgets.

Review basis:

- current main: `6a463b6fa4f4bd85ac3a944938004f6a9cfc80e3`
- PySide6 / Qt Widgets
- PyVista/VTK Room viewport
- dark-first Windows desktop product
- current canonical workspaces: Overview / Room / Measurements / Optimize
- RDC used for this planning pass: **0**

## Design diagnosis

The structural rewrite under #118 is materially better than the old dock-heavy composition. The remaining gap is no longer "add a dark theme".

The current application still visually reads as several local widget groups rather than one coherent design system.

Concrete examples:

### Shell

`WorkflowRail`:
- expanded width 184 px;
- compact width 112 px;
- text-only buttons;
- compact mode only hides the HTDT brand and reduces margins.

There is no icon-led compact representation.

`TopContextBar`:
- text buttons only;
- no overflow/adaptive policy;
- compact mode only hides the title/reduces spacing.

### Room

Current composition is approximately:

global rail
┌────────────────────────────────────────────────────────────┐

├────────────────────────────────────────────────────────────┤
│ context tool strip                                         │
├──────────────┬──────────────────────────────┬───────────────┤
│ object       │ overlay controls             │ inspector /   │
│ palette      ├──────────────────────────────┤ context panel │
│              │                              │               │

Each piece works, but the viewport is surrounded by several visually equal utility regions.

The 3D renderer also uses generic geometry for most object categories (#572).

### Overview

Current screen is:
- title;
- summary paragraph;
- warning/error cards;
- one primary next-action button.

It does not yet read as a mature project dashboard.

### Measurements / Optimize

Both have better page-first structure than the legacy GUI, but visual hierarchy still relies heavily on repeated raised cards/forms.

Repeated cards flatten importance:
- task header;
- primary result;
- helper explanation;
- advanced settings;
- status.

All can visually become "another box".

## Product design character

The target is:

> **technical, calm, spatial, high-density where useful, never dashboard-noisy**

Avoid:
- gamer/neon styling;
- glass everywhere;
- excessive pills;
- card-on-card nesting;
- rainbow category colors;
- huge marketing-style typography;
- icon-only mystery controls;
- photorealistic 3D as a requirement.

Prefer:
- neutral graphite surfaces;
- one controlled accent;
- strong spacing rhythm;
- persistent spatial context;
- concise Japanese task wording;
- dense numeric editing where the task benefits from it;
- scientific plots with restrained visual priority.

## 1. Global visual hierarchy

Use five levels only.

### L0 — Canvas / primary work

The thing the user is judging:
- 3D room;
- measurement plot;
- candidate comparison;
- validation result.

This receives the most area and contrast.

### L1 — Navigation

Global destination and local context.

Navigation must be visually quieter than L0.

### L2 — Task controls

Controls needed to complete the current task.

Examples:
- Draw room;
- Add speaker;
- Import REW;
- Generate candidates.

### L3 — Inspector / details

Precise values and selected-object details.
