## Summary

#905's primary-source finding: `qualify_clf` decodes UTF-8-SIG and returns `not_clf` on any decode failure — but the form manufacturers actually distribute to end users is the **secured binary `.CF1`/`.CF2`** (ODEON 19 manual §3.3, CATT directivity support, PRONOM fmt/1944+fmt/1945). A real distributed CLF binary was therefore reported as "not CLF", while all-green text fixtures falsely implied product compatibility.

Changes:

- `detect_clf_family(source)` — three-family classification: `authoring_text` / `binary_cf1` / `binary_cf2` / `unknown`. Binary detection uses the PRONOM signature only (lead `0x40|0x41 BD 0A 00 01`, `v{1,2}.0` at offset 20); truncated/unproven signatures fail closed to `unknown`.
- `ClfVerdict` gains `unsupported` — a recognized `.CF1`/`.CF2` is neither `not_clf` nor `qualified`: HTDT holds no licensed binary decoder, the payload is never parsed (rights boundary: binaries carry author identity/modification protection), and only manufacturer/user-legitimately-obtained tabular derivatives may proceed.
- `ClfQualification.family` records which family qualified.
- `INTERCHANGE_MATRIX` adds `binary_cf1`/`binary_cf2` as `user_import_candidate` (derivatives only, never the binary payload); clf1/clf2 basis reworded to "authoring text".
- Module docstring corrected — no longer claims CLF is a "plain-text interchange" as the distribution form.

`test_issue_905_clf_families.py`: 13 tests — signature-conforming synthetic fixtures (no real binaries, per the licensing action still open on the issue), truncated/wrong-marker fail-closed paths, binary-in-tail never parsed, text/unknown/empty/UTF-16 regression paths, matrix states.

Remaining on the issue (not code): licensed .CF1/.CF2 fixtures, ADR for a legal import route, end-to-end real-file verification.
