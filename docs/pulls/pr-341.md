```python
# native_cad.main, on failed guard.acquire(), non-maintenance:
for path in args.open_paths:
    forward_launch_intent(data_dir, build_launch_intent(path, source='forwarded'))
```

`'activate'` rides the existing at-least-once intent queue; the running instance already calls `raise_()`/`activateWindow()` before semantic dispatch, so `'activated'` short-circuits before any popup. File intents are queued *before* the activation so the document is open when the window comes forward.

**#11 restore-from-backup on the corrupted-store dialog:** `decide_launch` (stays pure, no I/O) gains `backup_restore_available`; the `バックアップから復元` choice renders only when the failure class is data-relevant (`restore_recommended`) AND ≥1 restorable archive exists. Choosing it opens Data Management and previews the newest archive through the existing validate→confirm→restore pipeline. `list_restorable_backups` merges automatic generations with pre-upgrade snapshots (`upgrade-recovery/`, previously invisible to every restore surface), ordered by filename-encoded creation stamp — never mtime.

**Found while wiring #11 — restore over a corrupt live store was impossible:** `_restore_backup` first ran `_create_backup` on the live DB, whose `_sqlite_health` check aborts on unreadable bytes — so the button's whole scenario vetoed itself. On pre-restore-backup failure the code now falls back to a raw forensic copy (`*-pre-restore-unverified-*.sqlite3`) and the journaled swap proceeds.

**Audit close:** Data Management's backup card could only restore via file picker — saved generations were invisible. Added a 保存済みバックアップ combo (hidden when empty) + "このバックアップを検証して復元…" button feeding the same preview path.
